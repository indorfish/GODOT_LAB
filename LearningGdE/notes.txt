-   Not that it's important, but the `.tcsn` file extension stands for "text scene".
It's just a text file and stores information about your scene in plaintext.
For example, here's one example:
```

offset_left = 146.0
offset_top = 98.00001

offset_bottom = 121.00001

```

-   According to the author of the game engine, it seems that you should dismiss MVC or Entity-Relationship diagrams when building in GdE.
You *can*, but that's not the natural paradigm for GdE design. GdEsign.
They say to conceptualize the elements your players will see in the game, and then build your code around those elements.
Then think about which elements can be said to instantiate which.
For example, in a PacMan clone, a Level or Stage can be said to instantiate ghosts, coins, and the maze.

INPUT-HANDLING IN GODOT
-   There's two general ways to do it.
`Input` is recommended for per-frame input handling i.e. when we want to handle input every frame. Perhaps synchronous input is what it's called?
That above sentence is not quite accurate but I'm keeping it anyway. Input is a singleton which means there's only one of it per running game.
`_unhandled_input()` is a virtual function for handling "asynchronous" input. Not really async per se, just intermittent - input that may arrive at any random time such as the user hitting the space key on their whim. It is an input callback, and you use it to determine what happens with certain input types. 
By default, all input is unhandled so you'll often see the 'ui' prefix as the symbolic names for these things.
